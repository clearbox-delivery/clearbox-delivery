# 外送員Mobile App前端功能白皮書

# 0) 整體設計風格

- **視覺**：純白設計，風格類似 ChatGPT 或 Threads，簡約流暢。
- **動效**：以「適時的流暢動畫」提升質感。
- 整體設計風格與顧客端 Mobile App 基本一致。

---

# 1) 註冊 / 登入頁（啟動後最先顯示）

## 1.0 進入與動效

- 完成下載並開啟 App 後，最先顯示「註冊登入頁」。
- **品牌 Logo** 先置中顯示，接著**慢慢往上移動**；Logo 下方**浮出 Email 與密碼輸入**。
- 按下「登入」進入 **CurrentOrders** 頁。
- **Email 為唯一登入方式**。
- 若尚未有帳號，點擊下方「註冊」小鍵進入註冊（臨時頁面，分三部分）。

## 1.1 註冊流程（臨時頁面：分三部分）

### （一）Email 驗證

- 輸入 Email，按「發送驗證碼」。收到後填入驗證碼欄位並按「驗證」。
- 若未收到，**在每次按「發送驗證碼」30 秒後**可按「重新送出驗證碼」。
- **裝置上限**：每個裝置在此 App **至多送出二十次**驗證碼，超過則鎖定不予驗證。

### （二）電話驗證

- 與 Email 驗證類似：輸入手機號碼 →「發送驗證碼」→ 填入 →「驗證」。
- 若未收到，**在每次按「發送驗證碼」兩分鐘秒後**可按「重新送出驗證碼」。
- **裝置上限**：每個裝置在此 App **至多送出五次**驗證碼，超過則鎖定不予驗證。

### （三）密碼設定

- 輸入「設定密碼」與「確認密碼」，按下註冊即完成並**直接登入**，進入 **CurrentOrders** 頁。

## 1.2 註冊限制與文案

- **同一 Email / 同一手機號碼**在此 App **都只能註冊一個帳號**。
- **同一部手機**在此 App **也只能註冊一次帳號**。
- 若在使用這次註冊資格前曾登入過其他既有帳號，**本次註冊資格會喪失**。
- 註冊頁面需小而清楚顯示文案：
    
    「**為了避免帳號的濫用，一個 Email / 一隻手機號碼都只能註冊一隻帳號；一部手機也只能註冊一次帳號。敬請愛惜您的帳號。**」
    

## 1.3 模擬器不可用（及開發期間處理）

- **必須確保模擬機無法使用 App**（正式環境）：
    1. 官方驗證服務
        - Android：**Google Play Integrity API**
        - iOS：**Apple App Attest / DeviceCheck**
        - → 驗證結果傳到後端，由後端決定是否放行
    2. **硬體金鑰**：手機在 Secure Enclave / Keystore 生成金鑰；伺服器隨機出題，手機以該金鑰簽名過關
    3. **驗證碼 / Captcha**：註冊或登入加入 **reCAPTCHA / Cloudflare Turnstile**
- **開發期間**需提供替代措施或暫時關閉模擬器檢驗，因為需以電腦測試與 `flutter run` 跑模擬。

# 2) 首次登入後的「初始資料」臨時頁面（不可跳過）

- 進入 CurrentOrders 頁後，在註冊後的第一次登入會跳出一個初始資料用的臨時頁面，這個臨時頁面分兩個部分。

### （一）**輸入真實姓名**

- 會請用戶先輸入自己的真實姓名。

### （二）**證件準備與拍攝**

- 會需要用戶備妥身分證、機車駕照、機車行照、良民證、銀行帳本，並且在保溫箱/袋上貼上我們品牌的Logo（此為台北市政府的規定）。
- 然後依序請外送員清楚地拍（直接調用用戶相機拍照，不讓用戶上傳已經拍好的照片）
    1. 身分證正反面
    2. 正面自拍
    3. 機車駕照正面
    4. 機車行照正面
    5. 良民證
    6. 銀行帳簿正面（外加手動輸入帳號）
    7. 機車保溫袋上的品牌Logo

- 初始資料的臨時頁面不能跳過。
- 但也要做開發期間的替代措施（如手動上傳照片）。因為在開發期間我們要用電腦來測試和flutter run跑模擬，沒辦法直接調用系統相機。

# 4) CurrentOrders 頁（接單主頁）

## 4.1 上方「需求熱度」視窗（H3 熱圖）

- 頁面中上方有一個視窗以顏色顯示以自己所在的H3, res = 10的格子為中心，附近k = 40內所有格子的需求熱度（由白至黃至橘至紅漸變，愈暖色調需求熱度愈高）。
- 熱度計算流程：
    1. 先計算需求熱度分數
        
        **S = （這個H3格子中正在等待被接的訂單數）/（這個格子中正在接單的外送員數+1）**
        
    2. 再統計這個外送員所在的格子為中心，附近k = 40內所有格子的 score，算 **P10 / P90 分位**，並正規化：
        
        **x=\text{clamp}\left(\frac{\text{score}-P10}{P90-P10},,0,,1\right)**。
        
    3. 再微調 γ讓中段更有層次：
        
        **x’ = x^{,1/\gamma}\quad(\gamma \in [1.2,1.6]，常用 1.4)**。
        
    4. 最後去閃爍，用指數移動平均（半衰期 2–3 分鐘）使時間平滑：
        
        **H_t=\alpha\cdot x’t+(1-\alpha)\cdot H{t-1}\quad(\alpha\approx0.2)**
        
        **H_t 就是要拿去上色的值（0–1）。**
        

## 4.2 「我要接單」按鈕與四段進度條

- 在這個視窗底下有一個上面寫著「我要接單」的大圓形按鈕，點下去後上方會以進度條顯示四個進度（分別是**1. 結算與找尋訂單 2. 前往店家 3. 店家等待 4. 前往顧客**）並進入第一個進度環節。

### 進度 1：結算與找尋訂單（含「單位時間收益排序（前端即時計算並排序）」）

- 在這個環節中會結算上一筆訂單（但如果並非連續接單下就沒有）並找尋訂單。
- 我們會先利用**自架的開源OSRM伺服器**算出**全台灣所有H3, res = 10對k = 40內除了自己外的其他所有格子的路程距離並打包儲存在資料庫**。
- 當外送員在這個環節時，我們會將**他目前所在的格子對k = 40內其他所有格子的路程時間資料**都丟給他的前端。

**（前端即時計算並排序）**

- 前端在接收到這些距離時間資料後，會根據我們定義的「單位時間收益排序」演算法即時計算並排列所有候選訂單的顯示順序。
- **每一筆訂單都會估算出「預期收入 R」與「預期耗時 T」，再以 R/T 得出單位時間收益（以元/分鐘），列表中所有訂單依據這個指標由高到低排序**，讓外送員能一眼看出哪些訂單最划算。
- **預期耗時 T** 同時考量三個部分：
    1. 外送員目前位置到店家的行程時間（依據之前打包送至外送員前端的「對k = 40內所有格子的路程時間資料」，找到對店家地址對應的H3格子的路程時間）；
    2. 店家備餐等待時間（依據店家在確認訂單時根據餐點內容手動輸入的候餐時間）；
    3. 店家到顧客的送餐時間（這會在顧客送出訂單時即時由OSRM計算，並將此資訊綁定至訂單，外送員端顯示時可以直接取用）。
- **預期耗時 T 的算法是**：
    
    **[max(外送員目前位置到店家的行程時間, 店家備餐等待時間) + 店家到顧客的送餐時間]，再取最小下限5分鐘，避免分母過小造成噪音。**
    
- **預期收入 R** 則是由**顧客自行決定的外送費金額**而定。
- **列表採即時更新**，在新訂單出現時要即時加入到正確的位置，訂單被接走也要即時移除訂單，同時做好**平滑動畫避免閃爍**。
- 這個排序機制能讓外送員接到報酬最高又耗時最短，最終達成**平均每工時收益最大化**。

### **進度 2：前往店家**

- 在接單後會進入第二個部分（前往店家）畫面，上面會顯示一個外送員騎著機車的圖片並寫著「請前往位於XXXXXX（地址）的XXXXX（店名）取餐」，並附上店家的Google Maps連結，我們的App不提供導航功能，需要外送員自行使用Google Maps導航至目的地。
- 在抵達目的地後，外送員要按下「我已抵達」，此時會跳出一個臨時畫面，直接調用外送員的相機拍照店家照片證明已抵達目的地。

### **進度 3：店家等待**

- 完成上述動作後進入第三個部分（店家等待）畫面，螢幕上會顯示取餐編號和一個臨時碼，此時會開始計時，顯示外送員等待的時間。
- 若時間達十分鐘，會跳出一個臨時頁面問外送員是否還要繼續等待或是直接結束這單。
- 在店家出餐後，外送員拿到餐點後會按「我已取餐」，此時會再跳出一個臨時畫面，直接調用外送員的相機拍照餐點照片證明已取餐，並要輸入店家端的臨時碼才算完成取餐手續。
- 接者就會跳到第四個部分（前往顧客）畫面，上面會顯示一個外送員騎著機車的圖片並寫著「請將餐點送達XXXXXX（地址）」，並附上顧客的Google Maps連結，我們的App不提供導航功能，需要外送員自行使用Google Maps導航至目的地。
- 畫面中有一個「我將於兩分鐘後抵達」的按鈕，點下此按鈕會發推播通知至顧客手機，提醒顧客取餐。

### **進度 4：前往顧客**

- 在抵達目的地後，按下畫面中的「我已抵達」按鈕，此時會跳出一個臨時畫面，直接調用外送員的相機拍照門牌照片證明已抵達目的地。
- 之後進入第五個部分（結算訂單）畫面，這個畫面會顯示此單賺到的外送費、拿到的分紅份數、總計用時（從接單至此時此刻），並且下面會有兩個主要按鈕，由左至右分別是「結束接單」和「繼續接單」，並且有一個舉報按鈕，用於檢舉顧客（包含不取餐等行為）。
- 在點下「結束接單」後就會跳回首頁；在點擊「繼續接單」後會顯示一個臨時畫面「辛苦了！請務必多補充水分並注意身體狀態，若有必要請讓自己休息10分鐘」並顯示「休息10分鐘」和「立刻接單」的按鈕。
- 在點擊「休息十分鐘」後這個臨時畫面會開始計時，當時間達到十分鐘時會提醒用戶「還要繼續接單嗎？」如果兩分鐘內未回應直接回到首頁，反之則進入第一個部分（找尋訂單）。

# 5) **OrderHistory頁**（歷史訂單）

- 畫面出現三個 Tabbar（由左至右分別是今日、本週和全部）

### （一）今日

- 最上方都會顯示今日上線時間、訂單數、外送費收益和分紅份數
- **列表順序**：由時間**近至遠**、**由上而下**顯示每一筆歷史訂單。
- **每筆顯示**：**店名、接單日期與時間、外送員接單至送達的時長、餐費金額、外送費金額**。
- 點擊「**V**」符號**展開**：顯示**詳細訂單內容**與「**評價店家**」按鈕

### （二）本週

- 最上方都會顯示本週累計上線時間、訂單數、外送費收益和分紅份數
- **列表順序**：由時間**近至遠**、**由上而下**顯示每一筆歷史訂單。
- **每筆顯示**：**店名、接單日期與時間、外送員接單至送達的時長、餐費金額、外送費金額**。
- 點擊「**V**」符號**展開**：顯示**詳細訂單內容**與「**評價店家**」按鈕

### （三）全部

- 最上方都會顯示全部上線時間、訂單數、外送費收益和分紅份數
- **列表順序**：由時間**近至遠**、**由上而下**顯示每一週的歷史資料，點進去可以看到歷史每一週的詳細資料，每週的顯示方式與（二）本週的顯示方式一致
